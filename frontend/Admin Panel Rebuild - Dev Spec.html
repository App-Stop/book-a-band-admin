Admin Panel Rebuild

Technical specification — entity-centric redesign for Users & Bands

Audience: Frontend + Backend 2026-09-27 v1

This spec replaces the current flat, route-per-page admin panel with an entity-centric one built around two things: a Dashboard, and a Users & Bands section where clicking into a user or band shows everything about them in tabs, instead of hunting across separate pages.

At a glance

  • Sidebar goes from 11 flat, route-mirroring pages to 7, organized by how admins actually look things up.
  • Users & Bands becomes the core screen: click into a user or band and see everything about them in tabs (bookings, payments, payouts, packages, disputes, etc.) instead of hunting across pages.
  • Bookings, Disputes, and Open Requests stay standalone and directly searchable — these are looked up by their own reference (a booking date, a case), not by the person.
  • Three concrete BUG fixes and one GAP (no Disputes page exists at all) are called out inline, verified against the live panel and the Mongoose schemas.
  • New: platform Revenue numbers on the Dashboard, which the panel currently shows nowhere.

Goal

Stop organizing the admin panel around database tables (one nav item per backend route) and organize it around the two entities an admin actually looks up: a user and a band. Almost every admin task — "what's going on with this band", "why is this user complaining", "where's this payout" — starts from one person or one band. Right now that means checking up to 5 different pages (Users, Bookings, Payouts, Band Packages, Reports) and cross-referencing IDs by hand. The rebuild puts all of it behind one search and one detail view, in tabs.

A handful of things genuinely are cross-entity queues (a report could be about any band, a support ticket about any user) — those stay as their own lighter list pages, described in What stays separate below.

Final navigation

Down from 11 flat items to 7. The split: entities (looked up by who they belong to) collapse into Users & Bands; records with their own reference number (a booking, a dispute, an open request — the kind of thing a customer quotes back to support, "my booking on Sept 28" or "case #123") keep their own searchable page, because an admin usually starts from that reference, not from the person.

  1. Dashboard

  2. Users & Bands — search + list → full entity detail in tabs (most day-to-day info lives here)

  3. Bookings — standalone, directly searchable by booking id, customer, band, date, status — no need to find the user first

  4. Disputes — standalone, directly searchable/filterable by status — currently has GAP no admin page at all (see gap below)

  5. Open Requests — standalone, for the force-expire workflow and "my request disappeared" tickets

  6. Moderation — tabs: Reports · Support Tickets

  7. Payouts — ops queue, defaults to failed / needs-action

(Platform Config stays as a reference page, reachable from Settings rather than the main nav.)

Band Packages, Posts & Comments, Reviews, and Band Analytics still fold into the entity detail view only — nobody looks those up by their own id, they're always "this band's packages" or "this band's posts."

Dashboard

No changes needed — the current one is already right: 8 count cards (Total Users, Total Bookings, Total Payouts, Open Requests, Total Posts, Pending Reports, Band Packages, Support Messages) plus a Quick Actions list. Keep it. Optionally make each count card and quick action a link straight into the relevant filtered view (e.g. "Pending Reports" → Moderation tab pre-filtered to pending).

Revenue (missing today)

Right now nothing on the panel tells the admin how much the platform is making — add it to the Dashboard as 2–3 numbers, not a full finance page:

  • Platform revenue (all time) — sum of platformFee across Payments with status paid/succeeded

  • Revenue this month — same sum, filtered to the current calendar month

  • Held in escrow / pending payout — sum of Payout.grossAmount for payouts not yet in status paid (i.e. money collected from customers that hasn't gone to a band yet) — useful because it's the platform's outstanding liability, not revenue

Don't try to net out refunds or build a trend chart for v1 — three honest totals beat a half-right graph.

Backend note: there's currently no dashboard-summary endpoint at all — the live panel gets its 8 count cards by calling /admin/users, /admin/bookings, /admin/payouts, etc. separately with limit=1 just to read each one's pagination.total. Worth adding one GET /admin/dashboard-summary that returns all of those counts plus the three revenue numbers in a single aggregation — cheaper for the panel to load, and revenue naturally lives there since it's not tied to any one list endpoint.

Users & Bands — list view

Keep the current table (it already works well): search by name/email, filter by role / status / email-verified, columns User · Role · Email · Status · Joined. One change: a row for a band-role user should show a small badge or subtitle with the band name, so admins can spot the band from the list without opening it — currently band accounts show as "Unnamed" in the list because it renders the user's fullName, which is often blank for band accounts (the real name lives on the Bands profile, not the User record).

Entity detail view — the core of the rebuild

Clicking a row opens one detail view with tabs. The tab set adapts to whether the row is a user, a band, or both (a user who is also a band owner gets both sets of tabs). This is the same drawer pattern the current User detail and Booking detail already use — keep that visual style, just widen what it shows.

Backend work required

All in services/AdminService.js / routes/Admin-Route.js:

  • Extend getUserById to also return, when the user has a band: payouts (Payout.find({ band: band._id })), packages (BandPackage.find({ bandId: band._id })), reviews (Review.find({ bandId: band._id, isDeleted: false })), posts (Post.find({ band: band._id })) — same pattern as the existing bookings/payments/disputes bundle, capped and sorted the same way

  • Add open-request participation to that same bundle for band accounts — reuse the aggregation from getBandAnalytics (services/AdminService.js) instead of writing a second version

  • Fix the payout amount field: the frontend needs payoutAmount (net to band), grossAmount, and platformFee — all already on the Payout model, just confirm the admin payout endpoints return them (they do — the bug is frontend-side, see below) and document the field names for the frontend dev

  • Same for Payment: the amount field is totalAmount, not amount — confirm and document

  • listUsers (or a lightweight join) should expose the band's fullName for band-role users, so the list view doesn't show "Unnamed" — currently only the User.fullName is selected, which is frequently blank for band accounts

  • Add GET /admin/disputes (list, filter by status/band/customer, paginated) and GET /admin/disputes/:id — GAP no dispute route exists today; disputes are only reachable buried inside getUserById/getBookingById, so there's no way to triage open disputes as a queue

  • Add a GET /admin/dashboard-summary endpoint returning all the Dashboard's count cards plus the three revenue numbers in one aggregation: platform revenue all-time and this-month (Payment.aggregate, sum platformFee where status in paid/succeeded), and escrow held (Payout.aggregate, sum grossAmount where status != paid) — replaces the current pattern of the panel calling ~8 separate list endpoints with limit=1 just to read each one's pagination.total

  • The backend list endpoints themselves (/admin/bookings, /admin/open-requests, /admin/band-packages, /admin/posts) don't need to change for the nav restructure — the standalone pages and the entity-detail tabs call the same endpoints, just with different filters (band/user query params already supported)

Frontend work required

Structural:

  • Collapse Posts & Comments, Band Packages, and Band Analytics out of the sidebar; rebuild as tabs on the Users & Bands entity detail view (spec above)

  • Keep Bookings as its own standalone, directly-searchable page — search/filter by booking id, customer, band, date, status. Admins usually start from a booking reference (a support ticket, a customer email), not from the user

  • Build a new standalone Disputes page — doesn't exist on the panel today at all; filter by status, search by booking/customer/band

  • Keep Open Requests as its own standalone page (force-expire workflow, "my request disappeared" tickets) rather than folding it into entity tabs

  • Merge Reports + Support Tickets into one "Moderation" page with two tabs

  • Keep a standalone Payouts page, but as an ops queue: default filter to failed / waiting_onboarding, with "all payouts" as a secondary filter, not the default

  • Add the Revenue numbers to the Dashboard (platform revenue all-time, this month, held-in-escrow — see Revenue section above)

Bug fixes found while reviewing the live panel:

  • BUG Payout/payment amounts show "—": the UI is reading a field like amount that doesn't exist on either model. Read payoutAmount (Payouts) and totalAmount (Payments/Bookings) instead — confirmed by reading the actual Mongoose schemas

  • BUG Booking status badge renders blank: the status label map only covers 5 values (pending, confirmed, completed, cancelled, expired), but bookingStatus actually has 10: pending_payment, confirmed, in_progress, completed, holding_funds, paid_out, disputed, cancelled, refunded, expired (constants/bookingStatus.js). Any booking in one of the missing 5 statuses shows a blank badge. Add all 10 to the label/color map

  • BUG Inconsistent filter controls: the Payouts page's status filter is a free-text box ("Status (e.g. failed)"); every other page uses a dropdown. Make Payouts a dropdown too, sourced from the same status enum

  • BUG Reports table overflows its container at normal desktop width — the Status column is cut off, requiring horizontal scroll. Needs a responsive fix (narrower columns, or wrap into the row like the entity-detail tabs do)

What stays separate, and why

Two different reasons something doesn't fold fully into the entity view:

Looked up by their own reference, not by the person — a customer quotes a booking date or a dispute back to support before anyone knows whose account it is. These need their own directly-searchable page even though they also show up inside the relevant user's/band's tabs:

  • Bookings

  • Disputes

  • Open Requests

Queues of things to decide on, not facts about one entity — an admin opens these without already knowing who's involved:

  • Reports — something was flagged before you know whose content it is

  • Support Tickets — a message arrives; you don't start from a profile

  • Payouts (ops queue) — "which payouts are stuck" is cross-band triage, even though a band's full payout history still lives on that band's Payouts tab

Everything else — Band Packages, Posts, Reviews, Band Analytics — really is just information about a specific band, so it only needs to live on that band's page.

Suggested build order

  1. Backend: extend getUserById with payouts/packages/reviews/posts, fix the amount field documentation, add the band fullName fix to listUsers

  2. Frontend: fix the three standalone bugs (amounts, status badges, Reports overflow) — quick wins, ship independently of the rest

  3. Frontend: build the tabbed entity detail view against the extended endpoint

  4. Frontend: remove the now-redundant sidebar items, merge Reports + Support into Moderation

  5. Both: re-point the Dashboard's count cards / quick actions at the new locations
